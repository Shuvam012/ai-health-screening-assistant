1. PROJECT OVERVIEW
================================================================================

Project Name:     AI Health Screening Assistant
Type:             Web Application (Voice-based AI Health Screening)
Purpose:          A web app where a user can have a live voice conversation
                  with an AI agent that conducts a basic health screening call.
                  Once the call ends, the app shows a structured health report
                  summarizing what was discussed.

How It Works:
  - User clicks "Start Call" → AI greets the user
  - AI asks health screening questions one at a time
  - User speaks → audio is captured and sent to backend
  - Backend transcribes speech → sends to LLM → generates audio response
  - AI asks adaptive follow-up questions based on context
  - User clicks "End Call" → structured health report is generated
  - Report displays: name, concern, symptoms, severity, duration, etc.

Current Phase:    Backend Only (React frontend to be built separately later)

2. ASSESSMENT REQUIREMENTS SUMMARY (FROM PDF)
================================================================================

MUST-HAVE FUNCTIONALITY:
  [1] The Call
      - "Start Call" button begins live voice conversation with AI
      - "End Call" button ends it
      - AI greets user, asks basic health-screening questions one at a time
      - Questions: name, main concern/symptom, duration, severity, related symptoms
      - Must feel like adaptive conversation, NOT a fixed script
      - Follow-up questions when answers are vague
      - Language: Hindi or English (minimum)
      - Transport: WebRTC, WebSockets, or similar (real-time oriented)
      - NOT "record whole conversation and upload one audio file at end"

  [2] The Pipeline
      - Speech-to-Text (STT) → LLM → Text-to-Speech (TTS)
      - Any APIs allowed (OpenAI/Whisper, Deepgram, ElevenLabs, etc.)
      - Push-to-talk style flow is ACCEPTABLE and EXPECTED
      - "user speaks their turn → sent for processing → AI responds → back to user"
      - Turn-taking and conversation state must be handled correctly
      - AI must remember what's already been asked and answered

  [3] The Report
      - Generated after call ends
      - Structured health report (not raw transcript dump)
      - Contains: main concern, key symptoms, duration, severity, follow-up items
      - Should read like something a doctor could glance at
      - Handle short/incomplete calls gracefully (no crash, no garbage)

NICE-TO-HAVE (OPTIONAL):
  - Auto language detection/switching
  - Barge-in handling (user speaks while AI is talking)
  - Graceful handling of silence, background noise, empty STT results

EVALUATION CRITERIA:
  - Does the call actually work (main thing)
  - Pipeline architecture (STT → LLM → TTS flow, real-time transport)
  - Conversation state management (context tracking across turns)
  - Failure handling (silence, unclear audio, API failures)
  - Report quality (synthesizes conversation into structured output)

3. TECHNOLOGY STACK (DETAILED)
================================================================================

RUNTIME & LANGUAGE:
  - Node.js (v18+)         — JavaScript runtime
  - TypeScript (v5.x)      — Type-safe JavaScript, strict mode enabled
  - ts-node / tsx           — Run TypeScript directly in development

WEB FRAMEWORK:
  - Express.js (v4.x)      — HTTP server, REST API routing, middleware

REAL-TIME COMMUNICATION:
  - ws (v8.x)              — WebSocket library for Node.js
                              Used for real-time voice conversation transport
                              Push-to-talk flow: client sends audio chunks,
                              server responds with AI audio

DATABASE:
  - MongoDB                 — NoSQL document database
  - Mongoose (v8.x)        — MongoDB ODM (Object Document Mapper)
                              Schema definitions, validation, queries

AI / ML APIs (OpenAI SDK + Groq):
  - openai (v4.x)          — Official OpenAI Node.js SDK (used for OpenAI & Groq endpoints)

  Speech-to-Text (STT):
    - OpenAI Whisper API    — Transcribes user audio using model: whisper-1
    - Groq STT API          — Alternative high-performance STT using model: whisper-large-v3
    - Supports: mp3, mp4, mpeg, mpga, m4a, wav, webm
    - Used for: Converting user speech to text each turn

  Large Language Model (LLM):
    - OpenAI GPT-4o-mini    — Drives the conversation
    - Structured JSON output — Returns reply + extracted health data
    - Used for: Generating AI responses, extracting health info,
                tracking conversation state, generating reports

  Text-to-Speech (TTS):
    - OpenAI TTS-1          — Converts AI text response to speech audio
    - Voice: alloy (configurable)
    - Output: mp3 audio buffer
    - Used for: Making AI responses audible to user

VALIDATION:
  - express-validator       — Request body/params validation for REST APIs

LOGGING:
  - winston (v3.x)         — Structured logging with levels and transports
                              Console transport in development
                              Levels: error, warn, info, debug

UTILITIES:
  - uuid (v9.x)            — Generate unique identifiers
  - dotenv (v16.x)         — Load environment variables from .env file
  - cors (v2.x)            — Cross-Origin Resource Sharing middleware
                              Needed for React frontend on different port

DEV DEPENDENCIES:
  - typescript              — TypeScript compiler
  - ts-node                 — TypeScript execution for Node.js
  - tsx                     — Fast TypeScript executor (alternative to ts-node)
  - nodemon                 — Auto-restart server on file changes
  - @types/express          — TypeScript types for Express
  - @types/ws               — TypeScript types for ws
  - @types/node             — TypeScript types for Node.js
  - @types/cors             — TypeScript types for cors
  - @types/uuid             — TypeScript types for uuid

WHY THESE CHOICES:
  - Express.js: Industry standard, simple, well-documented
  - ws: Lightweight, fast, native WebSocket (no Socket.IO overhead)
  - MongoDB/Mongoose: Flexible schema for varied health data, easy embedded docs
  - OpenAI: Single provider for STT+LLM+TTS reduces complexity
  - Winston: Production-grade logging with structured output
  - TypeScript strict: Catches bugs at compile time, better code quality

MODULE 3: AI Services (services/ai/)
─────────────────────────────────────────────

  stt.service.ts — Speech-to-Text
    Interface: STTService
      transcribe(audio: Buffer, mimeType?: string): Promise<string>
    
    Implementations:
      [1] OpenAIWhisperSTTService
          - Uses OpenAI Whisper API (whisper-1 model)
          - Accepts audio buffer, converts to file for API
          - Returns transcribed text string
          - Handles empty/unclear audio gracefully
      
      [2] GroqSTTService
          - Uses Groq STT API (whisper-large-v3 model)
          - Direct HTTP/REST call via OpenAI compatible baseURL
          - Returns transcribed text string
          - High performance and cost-effective
      
      [3] MockSTTService
          - Returns predefined transcription text
          - Cycles through sample responses for testing
          - No API key needed
    
    Factory: createSTTService(provider: string)
      - Returns appropriate implementation based on env config ('openai' | 'groq' | 'mock')

  llm.service.ts — Large Language Model
    Interface: LLMService
      chat(params: LLMChatParams): Promise<LLMResponse>
    
    LLMChatParams:
      - systemPrompt: string
      - messages: { role: string, content: string }[]
      - responseFormat?: 'json' | 'text'
    
    LLMResponse:
      - reply: string          (AI's spoken response)
      - collectedData: object  (extracted health information)
      - nextField: string      (what to ask next)
      - conversationComplete: boolean
    
    Implementations:
      [1] OpenAILLMService
          - Uses GPT-4o-mini with JSON response format
          - System prompt instructs structured output
          - Handles malformed JSON responses gracefully
          - Falls back to text-only response if parsing fails
      
      [2] MockLLMService
          - Returns scripted responses based on turn count
          - Simulates conversation progression
          - Returns mock collected data

    Factory: createLLMService(provider: string)

  tts.service.ts — Text-to-Speech
    Interface: TTSService
      synthesize(text: string): Promise<Buffer>
    
    Implementations:
      [1] OpenAITTSService
          - Uses OpenAI TTS-1 model
          - Voice: alloy (configurable via env)
          - Returns mp3 audio buffer
      
      [2] MockTTSService
          - Returns a small silent audio buffer
          - No API key needed

    Factory: createTTSService(provider: string)

  pipeline.service.ts — AI Pipeline Orchestration
    What it does:
      - Coordinates the entire audio-in → audio-out flow
      - Steps:
        1. Receive audio buffer from WebSocket
        2. Call STT service → get transcript text
        3. If transcript empty/unclear → return error message
        4. Load conversation history from DB
        5. Build LLM context (system prompt + history + collected data)
        6. Call LLM service → get response + extracted data
        7. Update call's collected data in DB
        8. Save user message + AI message to DB
        9. Call TTS service → get audio buffer
        10. Return: { transcript, aiText, aiAudio, collectedData }
      
      - Error handling at each step
      - If STT fails → tell user to repeat
      - If LLM fails → apologize and ask to repeat
      - If TTS fails → return text-only response

    Why separate from WebSocket:
      - Testable independently
      - Can be reused for other transports (REST, etc.)
      - Clear separation of concerns
      - Easier to debug each step

    What it does:

      2. Validates callId exists in database

      4. Sends AI greeting (text + audio)
      5. Listens for client messages:
         - audio.start → initialize audio buffer
         - audio.chunk → accumulate audio data
         - audio.end   → send buffer to pipeline, return response
         - call.end    → end call, generate report
      6. Handles disconnection → auto-end call if active
      7. Handles invalid messages → send error response
      8. Handles pipeline errors → send user-friendly error

      - Handle incomplete data gracefully
      - Add disclaimer that this is a screening, not a diagnosis
      - Output structured JSON matching HealthReport schema

8. AI PIPELINE — FULL FLOW
================================================================================

PIPELINE STEPS (for each user turn):

  Step 1: RECEIVE AUDIO
    ├── Source: WebSocket audio.end message
    ├── Format: Accumulated audio buffer from audio.chunk messages
    ├── Input: Raw audio bytes (base64 decoded)
    └── Output: Audio Buffer

  Step 2: SPEECH-TO-TEXT (STT)
    ├── Service: STTService.transcribe()
    ├── Provider: OpenAI Whisper API (or Mock)
    ├── Input: Audio Buffer + mime type
    ├── Output: Transcribed text string
    ├── Error handling:
    │   ├── Empty result → "I couldn't understand that, please repeat"
    │   ├── API failure → graceful error message to user
    │   └── Timeout → retry or error message
    └── Side effect: Send transcript message to client

  Step 3: LOAD CONTEXT
    ├── Service: ConversationService
    ├── Load: Conversation history (all messages for this call)
    ├── Load: Collected data (from Call document)
    ├── Build: System prompt with current state
    └── Output: Full message array for LLM

  Step 4: LLM PROCESSING
    ├── Service: LLMService.chat()
    ├── Provider: OpenAI GPT-4o-mini (or Mock)
    ├── Input: System prompt + conversation history + user transcript
    ├── Output format (JSON):
    │   {
    │     "reply": "How long have you had the headache?",
    │     "collectedData": { "mainConcern": "headache" },
    │     "nextField": "duration",
    │     "conversationComplete": false
    │   }
    ├── Error handling:
    │   ├── Malformed JSON → extract reply text, skip data update
    │   ├── API failure → apologize, ask user to repeat
    │   └── Timeout → retry or error message
    └── Output: AI reply text + extracted data

  Step 5: STATE UPDATE
    ├── Service: ConversationService.updateCollectedData()
    ├── Merge new collectedData into Call document
    ├── Save user message to Messages collection
    ├── Save AI message to Messages collection
    └── Update turn counter in Call metadata

  Step 6: TEXT-TO-SPEECH (TTS)
    ├── Service: TTSService.synthesize()
    ├── Provider: OpenAI TTS-1 (or Mock)
    ├── Input: AI reply text
    ├── Output: MP3 audio buffer
    ├── Error handling:
    │   └── API failure → return text-only response (no audio)
    └── Output: Audio Buffer

  Step 7: RESPOND TO CLIENT
    ├── Transport: WebSocket
    ├── Send: ai.response message with text + base64 audio
    └── Client plays audio and displays text

CALL END FLOW:

  Step 1: Client sends call.end (or disconnects)
  Step 2: Call status → 'completed'
  Step 3: Load full conversation history
  Step 4: Send to LLM with report generation prompt
  Step 5: Parse structured report
  Step 6: Save HealthReport to MongoDB
  Step 7: Send call.ended confirmation to client (if still connected)
  Step 8: Report available via GET /api/calls/:callId/report

9. WEBSOCKET PROTOCOL SPECIFICATION
================================================================================

ENDPOINT: ws://localhost:3001/ws/call/:callId

CONNECTION FLOW:
  1. Client creates call via POST /api/calls → gets callId
  2. Client connects to ws://localhost:3001/ws/call/{callId}
  3. Server validates callId
  4. Server sends ai.greeting message
  5. Client and server exchange messages (see below)
  6. Client sends call.end OR disconnects
  7. Server generates report and sends call.ended

─── CLIENT → SERVER MESSAGES ───

  Start Audio Recording:
    { "type": "audio.start" }
    Purpose: Signal that user is about to start speaking
    When: User presses "record" / "push-to-talk" button

  Audio Data Chunk:
    { "type": "audio.chunk", "data": "<base64-encoded-audio>" }
    Purpose: Send a chunk of recorded audio
    When: During recording, sent periodically
    Note: data is base64-encoded audio bytes

  End Audio Recording:
    { "type": "audio.end" }
    Purpose: Signal end of user speech, triggers AI pipeline
    When: User releases "record" button

  End Call:
    { "type": "call.end" }
    Purpose: End the screening call
    When: User clicks "End Call" button

─── SERVER → CLIENT MESSAGES ───

  AI Greeting:
    { 
      "type": "ai.greeting", 
      "text": "Hello! I'm your health screening assistant...", 
      "audio": "<base64-mp3>" 
    }
    When: Immediately after WebSocket connection established

  Processing Indicator:
    { "type": "ai.processing" }
    When: After audio.end received, before response ready
    Purpose: Client can show "AI is thinking..." indicator

  User Transcript:
    { 
      "type": "transcript", 
      "role": "user", 
      "text": "I have a headache" 
    }
    When: After STT completes, before LLM processing
    Purpose: Show user what was understood from their speech

  AI Response:
    { 
      "type": "ai.response", 
      "text": "How long have you had the headache?", 
      "audio": "<base64-mp3>" 
    }
    When: After full pipeline completes
    Purpose: AI's spoken response with audio

  Call Ended:
    { 
      "type": "call.ended", 
      "reportAvailable": true 
    }
    When: After call.end processed and report generated
    Purpose: Confirm call is over, report ready for retrieval

  Error:
    { 
      "type": "error", 
      "message": "I couldn't understand that. Could you please repeat?" 
    }
    When: Any error during processing
    Purpose: User-friendly error, never expose internals

  Role: Medical report generator

    - "Generate a structured health screening summary"
    - "This should read like something a doctor could glance at"

    - "Include recommendations for follow-up"
    - "Mark completeness based on available information"
    - "If conversation was cut short, note what's missing"
    - "Always include a disclaimer that this is not a diagnosis"
    
  Output format:
    JSON matching HealthReport schema

12. ERROR HANDLING STRATEGY
================================================================================

ERROR TYPE                  │ HANDLING
────────────────────────────┼────────────────────────────────────────
Empty STT result            │ Send "I couldn't understand, please repeat"
STT API failure             │ Log error, send user-friendly retry message
LLM API failure             │ Log error, send "sorry, please try again"
LLM malformed JSON          │ Try to extract reply text, skip data update
TTS API failure             │ Return text-only response (no audio)
MongoDB failure             │ Log error, return 500 with generic message
WebSocket disconnect        │ Auto-end call, generate partial report
Invalid WS message          │ Send error message, don't crash connection
Invalid call ID             │ Return 400/404 with clear message
User ends call early        │ Generate partial report, mark as 'partial'
API timeout                 │ Log timeout, send retry message
Unknown error               │ Log full details, send generic error to client

LOGGING:
  - All errors logged with full details via Winston
  - Stack traces in development only
  - No API keys or sensitive data in logs
  - Structured JSON logging in production

CLIENT-FACING ERRORS:
  - Always user-friendly language
  - Never expose internal details
  - Never show stack traces
  - Never show API keys or config
